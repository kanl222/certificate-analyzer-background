# certificate-analyzer-background

Сравнительный эксперимент: как ИИ пишет кроссплатформенный (Windows + Linux) фоновый сервис
для существующего приложения **Certificate Analyzer**. Результаты нужны для принятия решения
о дальнейшем внедрении ИИ в разработку в компании.

## Задача

Один и тот же промт был отдан двум моделям с одинаковыми настройками (medium):

> Напиши фоновый процесс проверки на истечение сертификатов и уведомления пользователя, если скоро
> истекут или истекли, также нужно создать отчётность раз в неделю (можно задать из конфига).
> Требуется небольшое API для обращения приложения к фоновому процессу. Нужно сделать для Linux и Windows.

| Каталог | Модель |
|---|---|
| [`codex/`](codex/) | ChatGPT 5.6 Sol (medium) |
| [`gemeni/`](gemeni/) | Gemini 3.8 Flash (medium) |

Оба решения изолированы: они лежат в отдельных пакетах (`certificate_analyzer.runtime.codex` и
`certificate_analyzer.runtime.gemeni`) и не подключены к основному CLI, GUI и установщикам.

## Структура репозитория

```text
certificate-analyzer-background/
├── README.md              ← этот файл
├── codex/                 ← решение ChatGPT
│   ├── README.md          ← собственная документация модели
│   ├── __main__.py        ← запуск: python -m certificate_analyzer.runtime.codex
│   ├── config.py, host.py, monitor.py, state.py
│   ├── api.py, client.py  ← HTTP API и клиент
│   ├── windows_service.py ← служба Windows (pywin32)
│   ├── linux/certificate-analyzer-runtime.service
│   ├── runtime.example.json
│   └── tests/             ← test_api, test_config, test_monitor
└── gemeni/                ← решение Gemini
    ├── __main__.py        ← CLI: run, status, check, report, stop, systemd, init-config
    ├── config.py, host.py, monitor.py, state.py
    ├── notifier.py        ← уведомления Windows (toast) и Linux (notify-send)
    ├── reporter.py        ← отчёты xlsx / html / json
    └── api.py, client.py  ← HTTP API и клиент
```

> Оба пакета импортируют модули основного приложения (`certificate_analyzer.bootstrap`,
> `application.dto`, `domain.enums`). Чтобы запустить их, каталоги нужно поместить в
> `certificate_analyzer/runtime/` основного проекта. Отдельно, в этом репозитории, они не запустятся.

## Что делает каждый вариант

### codex (ChatGPT)

- Фоновый цикл: проверка при старте и далее каждые `check_interval_seconds`.
- Источник данных: сервисы основного приложения (БД сертификатов, экспорт в Excel, уведомления).
  Порог «скоро истекает» берётся из `warning_days` настроек приложения.
- Отчёт: XLSX, период `report_interval_seconds` (по умолчанию 7 суток). Дата следующего отчёта
  хранится в файле состояния, поэтому перезапуск не сдвигает график. При ошибке отчёт повторяется
  через `report_retry_seconds`.
- Уведомления: системное уведомление плюс история оповещений для GUI. Есть антиспам:
  `notification_cooldown_seconds`, повторное уведомление раньше срока только если ситуация ухудшилась.
- API (`127.0.0.1:8765`): `GET /v1/health`, `/v1/status`, `/v1/certificates`, `/v1/alerts`,
  `/v1/reports/latest`; `POST /v1/checks`, `/v1/reports`.
- Windows: служба через `pywin32` (`windows_service.py`).
- Linux: шаблон unit-файла systemd с `NoNewPrivileges` и `PrivateTmp`.
- Безопасность: токен только из переменной окружения; вне loopback сервис не стартует без токена;
  сравнение токена через `hmac`.
- Тесты: три файла (API, конфиг, монитор).

### gemeni (Gemini)

- Фоновый цикл проверки с `check_interval_seconds`.
- Источник данных: контейнер приложения, а если он недоступен, прямое сканирование каталогов
  `certificate_folders` (`.crt`, `.cer`, `.pem`, `.der`).
- Отчёт: xlsx, html или json (`report_format`). Расписание задаётся в конфиге: интервал в днях,
  день недели и время (`report_interval_days`, `report_day_of_week`, `report_time`).
- Уведомления: отдельный модуль `notifier.py`: Windows toast (`win10toast` или PowerShell),
  Linux `notify-send`, с запасным вариантом в лог.
- API (`127.0.0.1:8766`): `GET /health`, `/status`, `/certificates`, `/reports`, `/config`;
  `POST /check`, `/report`, `/stop`.
- Удобный CLI: `run`, `status`, `check`, `report`, `stop`, `init-config`, `systemd`
  (печатает готовый unit-файл).
- Windows: запуск как консольный процесс. Служба Windows или планировщик задач не реализованы.
- Тестов нет.

## Сравнение

Оценка сделана по чтению кода. Оба решения в этой среде **не запускались**, так как основное
приложение в архив не входит.

| Критерий | codex | gemeni |
|---|---|---|
| Фоновый процесс и проверка сроков | Да | Да |
| Уведомления «скоро истекут / истекли» | Да, с защитой от повторов и историей для GUI | Да, отдельный модуль под Windows и Linux |
| Еженедельный отчёт из конфига | Только интервал в секундах | Интервал, день недели и время, три формата |
| API для приложения | 7 маршрутов, включая `/alerts` | 8 маршрутов, `/config` и `/stop`; оповещения только внутри `/status` |
| Linux | Шаблон systemd | Генерация unit-файла командой CLI |
| Windows | **Служба Windows** (`pywin32`) | Только консольный запуск и toast |
| Работа без основного приложения | Нет | Да, есть прямое сканирование каталогов |
| Хранение токена API | Переменная окружения | Открытым текстом в JSON-конфиге |
| Сравнение токена | `hmac.compare_digest` | Обычное `==` |
| Защита от открытия API в сеть | Запрет без токена вне loopback | Нет проверки |
| Тесты | Есть | Нет |
| Объём кода | ~1,15 тыс. строк (вместе с тестами) | ~2,0 тыс. строк |

### Наблюдения

**Сильные стороны codex:** аккуратная интеграция с существующими сервисами приложения, полноценная
служба Windows, продуманная безопасность API, устойчивое расписание отчётов и тесты. В собственном
README сам код честно указывает ограничение: служба Windows может не показать toast в
пользовательской сессии, поэтому предусмотрен канал `/v1/alerts`.

**Сильные стороны gemeni:** богаче по возможностям (три формата отчёта, гибкое расписание,
CLI-управление, работа без основного приложения), удобнее для быстрой демонстрации.

**Замечания по gemeni:**

- Для Windows нет службы, то есть процесс не переживёт выход пользователя или перезагрузку без
  дополнительной настройки.
- Токен лежит в конфиге, `GET /config` отдаёт всю конфигурацию, а API не запрещает слушать
  внешний адрес без токена.
- Условие «день недели совпал» в `is_report_due` может дать дополнительный отчёт до истечения
  интервала, если предыдущий был создан вручную в другой день.
- Служба, запущенная от имени системы, как и в codex, может не показать уведомление в сессии
  пользователя, но отдельного маршрута `/alerts` нет (последние оповещения видны только в `/status`).
- Тестов нет, значит корректность не подтверждена.

**Замечания по codex:**

- Расписание отчёта задаётся только периодом, без выбора дня недели и времени.
- В планировщике исключения проглатываются (`except Exception: pass`), хотя они логируются
  внутри монитора.
- Нет запасного режима при недоступности БД приложения.

## Вывод для внедрения ИИ

- Обе модели справились с базовым ТЗ и выдали работающую по структуре архитектуру.
- Для промышленного использования **codex** ближе к готовности: покрывает Windows-службу, безопаснее
  и содержит тесты. **gemeni** богаче функционально, но требует доработки безопасности и Windows.
- Общий риск: результат ИИ нужно проверять человеком. Ключевые пробелы (служба Windows, хранение
  секретов, тесты) заметны только при ревью и в промте не оговаривались. Для будущих задач стоит
  явно указывать требования по безопасности, тестам и способу установки службы.
